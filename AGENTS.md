# Project rules

- Turkish-language mobile-first prototype rendered inside a 390x844 device frame (`src/components/layout/AppShell.tsx`); `/dashboard` renders full-width outside the frame. Why: presentation demo on desktop, real phone on mobile.
- No backend: all state lives in per-feature zustand stores persisted to localStorage with `skipHydration`, rehydrated once in AppShell before rendering. Why: avoids SSR hydration mismatches.
- Feature code lives in `src/features/{videoSupport,qrSupport,aiAgents,family,help,demo,core,workflow,scenario,giga}`; page components in `src/screens`; route files in `src/routes` stay thin (import + head). Why: TanStack forbids `src/pages`; keeps routes declarative.
- Classic demo triggers and global reset/rehydrate live in `src/features/demo/scenarios.ts`; every new persisted store must be added to `resetAll`/`rehydrateAll` there. Why: one place for reset and hydration.
- Autonomous processes go through `src/features/workflow/engine.ts` (central statuses, dedupe keys, completion guards, audit, notifications, persisted delayed ops); services in `workflow/services/*` call only `mockServices.ts` adapters for external systems. Why: one state machine for all features, swappable for real APIs.
- Presenter scenarios (`src/features/scenario`) only call real service functions and derive step state from workflow data, never their own copies; `ScenarioDriver` runs the op queue and auto-play. Why: panel and phone can never diverge.
- Zustand selectors must return stored references; filter/sort after selecting. Why: selectors that build new arrays cause infinite re-render loops.
- All mock data and copy constants come from `src/data/mock.ts`. Why: single source for demo content.
- Overlays/sheets use `position: fixed` inside the transformed phone frame instead of Radix portals. Why: portals would escape the device frame.
- Business rules with tests live in pure modules (e.g. `src/features/workflow/rules.ts`) covered by `src/test/*.test.ts`; `src/test/platform.test.ts` plays every presenter scenario outcome end to end. Why: scenario regressions surface without a browser.
- Analytics: call `track()` / `useFlow()` from `src/lib/analytics.ts`; events go to console and the app store for the dashboard.
- Customer-facing workflow wording comes only from `STATUS_LABEL` (rules.ts) and `src/features/workflow/copy.ts`; technical detail goes to the audit log / `TechDetails`. Why: the same state must read the same everywhere.
- `notify()` defaults to push; routine progress passes `"quiet"` and in-flow `ask()` calls pass `{ push: false }`. Why: phone pushes only for decisions, milestones, delays, new processes and resolutions.
- Outages and the free Hibrit İnternet run only through `src/features/workflow/services/hybrid.ts` (single `outage` + `hybrid` state in the workflow store; presenter controls in `src/features/scenario/HybridControls.tsx`); the Hibrit screen's status text and tiles come only from the pure `hybridView()` and its top outage card (cause, estimated fix time; shown whether the backup is on or off) only from the pure `outageInfo()` (`src/features/workflow/hybridView.ts`, tested in `src/test/hybrid-view.test.ts`), which treats the main line as down whenever `connectivity.fixed` is down or an outage is open. The home outage card is only the Hibrit İnternet toggle (`HybridSwitchCard`); it and the Hibrit screen's open button read the pure `hybridSwitchView()` / call only `setHybridOn()`/`openHybridBox()` (on/off with a mock loading phase via `hybrid.switched`), so they cannot diverge. Why: one outage source keeps every surface in sync, and the page can never say "normal" while the main line is down.
- The assistant brand is defined once: copy/capabilities in `GIGA` (`src/data/mock.ts`), avatar/name/action-mode tag in `src/features/giga/GigaAvatar.tsx`, request understanding in the pure scored classifier `src/features/giga/intent.ts`, replies in the pure `src/features/giga/assistant.ts` (tested in `src/test/giga.test.ts` and `src/test/giga-intent.test.ts`), and request-to-process starts only via `launchIntent` in `src/features/giga/actions.ts`. `GigaNote`/`GigaAvatar` appear only in conversational, troubleshooting or diagnosis UI; ordinary feature screens use `PlainNote` (primitives) and their established names, guarded by `src/test/brand-trust.test.ts`. Why: one assistant identity, used where AI actually helps, and chat replies can never claim an action the workflow services didn't perform.
- Live support, auto-payment and relocation team matching are workflow services (`services/liveSupport.ts`, `services/autopay.ts`, `migration.ts` team ops) with state in the workflow store (`chats`, `autoPay`, `config.teamMatch`). Why: every simulated channel shares one persisted source and is covered by `src/test/journeys.test.ts`.
- Notification merging and push permission are pure rules in `src/features/core/notifications.ts`, used by `appStore.notify` (pushes also feed the presenter's `LockPhone`). Why: "combine repeated updates" stays testable and consistent for every sender.
- GIGA Teknik (`services/aiUsta.ts`) always runs digital repair (simulated remote checks, outcome from `config.ustaDiag`) before any modem inspection; every customer decision offers `LIVE_OPTION`, which escalates with `handoffSummary` context and opens the live chat (tested in `src/test/usta.test.ts`). Why: diagnose remotely first, never ask for photos too early, never make the customer repeat themselves.
- The GIGA screen (`/ajanlar`, `AgentCenterScreen`) is the single support entry: every "ask GIGA" input calls `appStore.openHelp(text)`, AppShell routes to `/ajanlar`, and the screen sends the text. The conversation lives in the in-memory `src/features/giga/chatStore.ts`; processes GIGA starts render live inside the chat (`DecisionCard`/`AiUstaPanel` reused). Automatic-check toggles live on `/ajanlar/kontroller`. Why: one entry point, context kept while visiting process pages, no duplicate flow UI.
